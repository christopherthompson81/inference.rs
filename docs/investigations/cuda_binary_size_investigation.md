# CUDA binary size investigation

Motivation: inference.rs is meant to be bundled into other projects through the C ABI, so the size of a CUDA build of
`libinference_ffi` matters. The comparable is llama.cpp's own CUDA build (`build_cuda`: Release, `GGML_NATIVE=ON`,
`BUILD_SHARED_LIBS=ON`, `GGML_CUDA_FA=ON`), which ships `libggml-cuda.so` plus `libllama.so`, `libggml-base.so`,
`libggml-cpu.so` and `libggml.so`.

## Run 1 - 2026-10-03 08:20

Question: are the two builds targeting the same GPU code, and how big is each side's device code?

Command: `cuobjdump -lelf -lptx` and `size -A` on llama.cpp's `bin/libggml-cuda.so.0.22.0` and on the four dev kernel
libraries under `target/debug/cuda-kernels/`.

Finding: both build SASS for sm_86 only (the RTX 3090), with no PTX; ours also carries one sm_52 stub image per
library. Device code (`.nv_fatbin`):

| library | `.nv_fatbin` | images |
|---|---|---|
| llama.cpp `libggml-cuda.so` (whole file 37.5 MiB) | 15.8 MiB | 142 |
| `libflashattention.so` | 231.1 MiB | 53 |
| `libinferencequant.so` | 138.8 MiB | 70 |
| `libinferencepagedattention.so` | 104.6 MiB | 30 |
| `libinferencecuda.so` | 16.5 MiB | 30 |
| ours, total | 491.0 MiB | |

The biggest objects: each Dao FA2 instance (hdim 32-512, fp16/bf16, causal, split-kv) is 2-7.5 MiB; paged attention
v1/v2 per dtype is 5-11 MiB; `mmvq_iqk` 9.0 MiB, `mmvq_gguf` 6.0 MiB, `mmvq_kt` 5.6 MiB, and each mmq instance 3-4 MiB.

Implication: a 31x gap in device code at the same arch. The instance counts are the same order of magnitude
(142 vs 183), so the per-image size, not the kernel count, needs explaining first.

## Run 2 - 2026-10-03 08:35

Question: llama.cpp passes `-compress-mode=size` (`GGML_CUDA_COMPRESSION_MODE`, default `size`, CUDA 12.8+); only
inference-nn's FlashInfer GDN builder (SM90-only, so not in this sm_86 build) passes any (`-Xfatbin=-compress-all`). How much of the gap is compression?

Command: extract every sm_86 cubin from each of our libraries (`cuobjdump -xelf all`), then repack them with
`fatbinary --create` uncompressed, with `--compress-all`, and with `--compress-mode=size` (CUDA 12.8).

Finding:

| library | uncompressed | `--compress-all` | `--compress-mode=size` |
|---|---|---|---|
| flashattention | 231.1 MiB | 66.8 MiB | 28.3 MiB |
| inferencequant | 138.7 MiB | 38.8 MiB | 18.1 MiB |
| inferencepagedattention | 104.6 MiB | 60.6 MiB | 13.7 MiB |
| inferencecuda | 16.5 MiB | 2.9 MiB | 0.9 MiB |
| total | 491 MiB | 169 MiB | 61 MiB |

Implication: compression accounts for 8x of the 31x. With `-compress-mode=size` on every kernel crate, device code is
about 61 MiB vs llama.cpp's 15.8 MiB. The rest is kernel scope: FA2's 53 instances (28 MiB compressed) alone exceed
llama.cpp's whole fatbin, and paged attention adds another 14 MiB. Next: measure the host side and the real bundled
artifact with a release build (`cargo build --release -p inference-ffi --features "cuda flash-attn cudnn"`).

## Run 3 - 2026-10-03 08:50

Question: what does the artifact a project would bundle look like? The dev libraries above carry line-table debug info
and split kernels into shared libraries; release links everything into one `libinference_ffi.so`.

Command: `cargo build --release -p inference-ffi --features "cuda flash-attn cudnn"` (2m 46s, kernels from the nvcc
ccache), then `size -A`, `strip`, `readelf -d`, `nm -S` grouped by crate prefix, and a scan of `.rodata` for PTX text
(`// Generated by NVIDIA NVVM Compiler` headers).

Finding: 682 MiB on disk, 628 MiB stripped.

| section | size | what |
|---|---|---|
| `.nv_fatbin` | 492.2 MiB | the four kernel crates' SASS, uncompressed (Run 1) |
| `.text` | 64.4 MiB | host code: candle_core 10.6 MiB, std/core/alloc generics ~10 MiB, C/C++ host stubs 6.4 MiB, model crates ~5 MiB together |
| `.rodata` | 55.8 MiB | 50.0 MiB of it is candle-kernels' PTX: 38 modules, 2,905 entries, JIT-compiled by the driver at load |
| rest | ~16 MiB | unwind tables, relocations |

llama.cpp's equivalent (libllama 4.5 MiB, libggml-cuda 37.5 MiB, ggml-base 0.9 MiB, ggml-cpu 1.1 MiB, ggml 0.05 MiB) is
44 MiB in all.

Runtime libraries (`NEEDED`): llama.cpp's CUDA backend needs cudart, cuBLAS and cuBLASLt (~830 MiB with CUDA 12.8).
Ours needs those plus cuRAND (130 MiB), NVRTC (106 MiB with builtins) and, with the `cudnn` feature, cuDNN 9 (~1.15 GB
over its sub-libraries). For a bundle that ships the CUDA libraries, those dependencies outweigh our own library.

Implication, ranked by size saved per effort:

| lever | saves | notes |
|---|---|---|
| `-compress-mode=size` in every kernel crate's build script | ~430 MiB | Run 2 repack; check module-load time, the driver decompresses on load |
| leave `cudnn` out of bundled builds | ~1.15 GB of runtime deps | check which ops use it and their non-cuDNN fallbacks |
| candle-kernels PTX: ship compressed SASS instead | ~45 MiB | needs a candle-kernels build change; also removes the first-load JIT |
| cuRAND, NVRTC as dependencies | ~236 MiB of runtime deps | find the call sites; they may be avoidable or loadable on demand |
| FA2 instance scope (53 instances, 28 MiB compressed) | up to ~25 MiB | a feature decision: which head dims and split-kv variants are needed |
| host `.text` (LTO, codegen-units=1) | unmeasured | 64 MiB vs llama.cpp's ~22 MiB of host code; ours also carries the agent, MCP, audio and TLS stacks |

Projected with the first and third levers: ~150 MiB, vs llama.cpp's 44 MiB.

## Run 4 - 2026-10-04 06:30 (approximate)

Step 1 of #258: compress the fatbins.

Change: `KernelBuilder::compress_fatbin` in the vendored cudaforge passes `-compress-mode=size` from CUDA 12.8 and
`-Xfatbin=-compress-all` before it. Every kernel builder calls it: flash-attn, quant (main, DeepGEMM, NVFP4), nn (main,
FlashInfer GDN, which replaces its own `-compress-all`), and paged-attn (main, FA3).

Question: does the real build match the Run 2 repack, and what does decompression cost at load?

Command: `cargo build --release -p inference-cli --features "cuda flash-attn cudnn"` with and without the change, then
`size -A` on the binary, and load + first-token timing on `Qwen3.5-0.8B-Q8_0.gguf`.

Finding:

| release `inference` CLI | file | `.nv_fatbin` | launch to first token (8 runs) | prefill 512 | decode 128 |
|---|---|---|---|---|---|
| uncompressed | 671 MiB | 492.2 MiB | 1.83-1.91 s, median 1.855 s | 21.1k +/- 2.0k tok/s | 559 tok/s |
| `-compress-mode=size` | 241 MiB | 62.2 MiB | 1.86-1.95 s, median 1.875 s | 22.7k +/- 0.1k tok/s | 558 tok/s |

The cold timing is `inference bench -f Qwen3.5-0.8B-Q8_0.gguf --prompt-len 16 --gen-len 1 --iterations 1 --warmup 0`
under `/usr/bin/time`, with the two binaries interleaved. Prefill and decode are `--prompt-len 512 --gen-len 128`.

Notes:
- The bench model is a symlink in a directory of its own. Next to `/mnt/data/models`' stray `mmproj-BF16.gguf`, the
  GGUF projector auto-selection picks that file and fails with a base-model metadata mismatch.
- The first compressed release build took 37 min: the flag changes every kernel's nvcc command, so ccache misses. The
  uncompressed rebuild took 1m 42s from cache.

Implication: the repack estimate holds (61 MiB projected, 62.2 MiB built). On this workload the compressed launch is
20 ms slower at the median (the whole range sits 30-40 ms higher), within run-to-run noise but not ruled out. Paged
attention is on by default on CUDA, so this run loaded it (Run 6 corrects an earlier note here that it did not).
Whether this run exercised FA2 was not checked. The prefill gap is the uncompressed run's +/- 2.0k variance, not a change; decode is identical. Step 1 is done; candle-kernels' PTX (`.rodata`,
67 MiB in the CLI) is now the largest GPU-side item.

## Run 5 - 2026-10-04 07:00 (approximate)

Step 2 of #258. Question: where does the 50 MiB of PTX in `.rodata` come from? candle-kernels' 11 modules are only
10.6 MiB (`target/debug/build/candle-kernels-*/out/*.ptx`, 705 entries), and no other crate builds PTX.

Command: scan built binaries for NVVM PTX headers, keyed by each blob's first `.entry` name.

Finding: the modules are duplicated. In the CUDA integration-test binary: 38 blobs; the binary-ops module (2.3 MiB)
13 times, unary 5, reduce 4, the rest twice. In `inference_core`'s test binary: 24 blobs. The cause is
`candle-kernels/src/lib.rs`: each module is a `pub const X: Module` over an `include_str!` const, and every use of a
const in another codegen unit or crate embeds its own copy of the string. candle-core takes every module by reference
(`get_or_load_func(name, &kernels::X)`), so `pub static` keeps its API.

Change: vendor candle-kernels at our candle rev into `third_party/candle-kernels`, patched in through
`[patch."https://github.com/huggingface/candle.git"]`. The `mdl!` items become statics, and the MoE/mmq/mmvq archive it
links statically calls `compress_fatbin()`.

Finding (`cargo build --release -p inference-ffi --features "cuda flash-attn cudnn"`, 3m 36s):

| `libinference_ffi.so` | file | stripped | `.rodata` | `.nv_fatbin` | PTX blobs |
|---|---|---|---|---|---|
| master before #259 (Run 3) | 682 MiB | 628 MiB | 55.8 MiB | 492.2 MiB | 38 |
| this change | 180.0 MiB | 157.4 MiB | 16.4 MiB | 61.1 MiB | 11 |

The baseline row also predates #259's compression; no post-#259 `libinference_ffi.so` was measured. This change's own
effect is the `.rodata` drop (39.4 MiB, the 50.0 - 10.6 MiB of duplicate PTX) and 1.1 MiB of `.nv_fatbin` from
compressing candle's archive. The 13/5/4 per-module breakdown above is from the integration-test binary; on the `.so`
only the blob count (38, then 11) was checked.

## Run 6 - 2026-10-04 07:10 (approximate)

Question (owed from Run 4): is the compressed build's launch cost still invisible on a safetensors model with paged
attention forced on? And what does the remaining PTX cost at load?

Command: `inference bench -m Qwen3.5-0.8B --prompt-len 512 --gen-len 1 --iterations 1 --warmup 0 --paged-attn on`
under `/usr/bin/time`, three binaries interleaved (Run 4's uncompressed and compressed CLIs, and a release CLI built
from this change with `cargo build --release -p inference-cli --features "cuda flash-attn cudnn"`, 2m 26s), then again
with `CUDA_CACHE_DISABLE=1`. Qwen3.5 is a hybrid with GDN layers; whether its full-attention layers took the FA2 path
was not checked.

Finding (seconds, launch to first token):

| binary | run 1 | runs 2-6 | `CUDA_CACHE_DISABLE=1` |
|---|---|---|---|
| uncompressed | 2.13 | 1.97-1.99 | 16.97, 16.94 |
| compressed (#259) | 2.02 | 1.99-2.05 | |
| deduplicated PTX | 6.88 | 1.98-2.02 | 17.00, 16.86 |

Steady state (`--prompt-len 512 --gen-len 128 --paged-attn on`, this change): prefill 20.9k +/- 2.1k tok/s, decode
396 tok/s (safetensors, BF16).

Implication:
- Compression costs nothing measurable on this model either.
- The PTX costs ~15 s of driver JIT whenever the compute cache misses: a fresh machine, a container without a
  persistent `~/.nv`, or an eviction. The new binary's first run (6.88 s) is unexplained: all three embed byte-identical PTX, so
  the earlier runs should have filled the cache; an eviction is possible but was not shown. `~/.nv/ComputeCache` is
  228 MiB against the driver's 256 MiB default `CUDA_CACHE_MAXSIZE`. Every candle module is loaded at startup
  (`preload_candle_ptx`, inference-core/src/inference_rs/mod.rs), so the whole 10.6 MiB is JIT-compiled on a miss.
- For a bundled library that is a worse problem than the 10.6 MiB. Shipping SASS for candle's modules fixes both, but
  candle-core loads them with `load_module(mdl.ptx().into())` from a `&str` (cuda_backend/device.rs:350). Loading a
  fatbin needs `Ptx::from_binary`, which means patching candle-core as well, not only candle-kernels.
