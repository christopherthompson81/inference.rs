# DeepSeek-OCR investigation

Issue #551: DeepSeek-OCR 1 and 2 (and Baidu's Unlimited-OCR on OCR 1's architecture). Phase 1 is DeepSeek-OCR 1 from
safetensors and from llama.cpp's GGUFs.

The test page throughout is a synthetic one, generated by a script (1240x1600: a title, three section headings, a
paragraph of invented sentences, a 4x4 table of invented numbers, a notes paragraph). It takes a 2x3 grid of tiles.

## Run 1 - 2026-11-16 23:35

**Question:** what does transformers' reference produce, and what do its intermediates look like?

The checkpoint's remote code (`modeling_deepseekocr.py`, `deepencoder.py`) imports `LlamaFlashAttention2`, which
transformers dropped after 4.46, so the reference runs in a venv on transformers 4.46.3 with the system torch
(`/mnt/data/dsocr-venv`, `--system-site-packages`). `infer(base_size=1024, image_size=640, crop_mode=True,
eval_mode=True)`, the reference's "Gundam" mode, with the prompt `<image>\n<|grounding|>Convert the document to
markdown.`, bf16 on CUDA. Hooks save SAM's input and output, CLIP's output and the projector's.

```
global view (1, 3, 1024, 1024) -> SAM (1, 1024, 16, 16) -> CLIP (1, 257, 1024) -> projector (1, 256, 1280)
tiles       (6, 3, 640, 640)   -> SAM (6, 1024, 10, 10) -> CLIP (6, 101, 1024) -> projector (6, 100, 1280)
prompt: 913 tokens = BOS + 630 tile tokens (3 x 10 rows of 2 x 10 + newline) + 273 global (16 x 17 + 1) + 9 text
```

The output is the page exactly: every heading, the paragraph and the notes, the table as `<table><tr><td>...`, each
block tagged `<|ref|>kind<|/ref|><|det|>[[x0, y0, x1, y1]]<|/det|>`.

Two details of the reference worth recording. The prompt lists the global view's tokens first, but the features
scatter in as tiles, then the global view, then the separator; every image token has one id, so only the scatter
order matters, and llama.cpp's matches it (`ov_img_first = false`). And `dynamic_preprocess` sorts a `set` of grids by
tile count, so grids with equal counts keep Python's hash order; that decides only an aspect exactly between a grid
and its transpose (1.25 between 1x2 and 2x1). Ours takes insertion order, as llama.cpp does.

## Run 2 - 2026-11-16 23:55

**Question:** does our SAM match the reference's bottom up, before the rest is built on it?

A throwaway test loaded `inference_nn::vision::sam::SamEncoder` from the checkpoint (bf16, CUDA) and ran the
reference's saved SAM inputs.

```
1024 global view (its own 64x64 grid)                          cos 0.99960  max |diff| 0.017
640 tiles (position embedding and global rel-pos resampled)    cos 0.99972  max |diff| 0.010
```

bf16 against bf16, both resamples included (antialiased bicubic for the absolute positions, linear for the global
layers' relative tables). The window blocks pad 64 and 40 up to 70 and 42 with zeros that stay in the attention as
keys, as the reference's do.

## Run 3 - 2026-11-17 00:00

**Question:** end to end on the real checkpoint and on llama.cpp's GGUFs, against the reference and llama.cpp.

`inference serve -m /mnt/data/models/deepseek-ocr`, one greedy request, the same prompt.

```
safetensors (bf16)    913 prompt tokens, 311 out at 326 tok/s on the 3090
                      equal to the reference but one digit: a box's 498 / 499, an exact tie in our logits
                      (both -0.928)
small crop (600x400, no tiles, `Free OCR.`)   278 prompt tokens, equal to the reference
text only             "The capital of France is Paris."
```

The first run lost every tag: the tokenizer marks all 816 of its added tokens special, the layout and table tags
among them, and the reply decoded without special tokens (`<table>ItemWidthHeight...</table>`). The reference
decodes with `skip_special_tokens=False`. A loader now says its special tokens are part of the reply
(`output_special_tokens`), which keeps them all but the token that stops it.

GGUF: ggml-org/DeepSeek-OCR-GGUF Q8_0 text and Q8_0 projector, ours and llama-server (970b51ce7) on the same files.

```
ours           913 prompt tokens; the text equal to the reference, five box digits off by 1 or 2
llama.cpp      913 prompt tokens; the text equal to the reference, six box digits off by 1, no tags
ours vs llama  two splits, both near ties: 804 / 803 (llama.cpp ties them at -1.602, ours 0.09 apart) and
               904 / 905 (ours 0.03 apart); max |d top logprob| over the 60 tokens before the first 0.082
```

llama-server drops the special tokens from its text, so its table comes back as bare cell contents.

The GGUF needed: our template over the GGUF's (`{% for m in messages %}{{m['content']}}{% endfor %}`, which writes no
image marker), the `<image>` id read from the GGUF's vocabulary, the config built from metadata (the GGUF repo ships
no `config.json`; SAM's global layers are llama.cpp's fixed 2, 5, 8, 11, as is the 1024 global view), and the rotary
pairing half-split (llama.cpp ropes this text stack NeoX-style over the whole head).

A suspected llama.cpp issue, from its graph: the mmproj keeps CLIP's position table in the checkpoint's order (the
class row first; GGUF row 0 equals the checkpoint's row 0 exactly), but for a tile, whose grid differs from the
table's, `clip_graph_deepseekocr::build` resamples rows 0..256 as the patch grid and takes row 256 as the class
position. That resamples the class row in with the patches and drops the last patch row's position. On this page the
effect is small (llama.cpp's text is the reference's), so it is noted here, not measured.
