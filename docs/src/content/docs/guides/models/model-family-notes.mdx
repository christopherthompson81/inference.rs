Most models need nothing beyond `inference run -m <id>` (see [Run models](/guides/models/run-any-model/)). This page collects the per-family exceptions. The full architecture inventory is in the [supported models reference](/reference/supported-models/).

## Reasoning controls

`reasoning_effort` accepts `off`, `low`, `medium`, `high`, and `xhigh`; `none` is an alias for `off`. If no effort is set, inference.rs leaves it unspecified and enables thinking. An explicit positive effort enables thinking, while `off` disables it. The legacy `enable_thinking` boolean remains supported, but contradictory explicit values return an error.

These controls are template inputs, not sampling parameters. inference.rs passes an explicit effort under both `reasoning_effort` and the template compatibility name `reasoning_strength`. Each model's template decides whether it distinguishes every positive tier.

## Thinking models (Qwen3, SmolLM3)

Qwen3 and SmolLM3 are hybrid reasoning models; their chat templates enable thinking by default. Toggle it per request. Inline `/think` and `/no_think` prompt tags work everywhere; the `--thinking` flag and the `enable_thinking` field do the same without editing user text (`true` forces on and `false` forces off).

<Tabs>
<TabItem label="CLI">

```bash
inference run --thinking false -m Qwen/Qwen3-4B
```

`--thinking` and `--reasoning-effort` apply to both one-shot and interactive use. Prompt tags also work inline:

```text
How many rs are in blueberry? /no_think
Are you sure? /think
```

Qwen3 also publishes FP8 pre-quantized checkpoints; pass the FP8 model ID directly when you want
those weights instead of runtime [ISQ (in-situ quantization)](/reference/quantization-types/).
For example, Qwen3.8 can serve published block-FP8 weights and an FP8 paged KV cache together:

```bash
inference serve -m Qwen/Qwen3.8-27B-FP8 --pa-cache-type f8e4m3 --max-seqs 16
```

The checkpoint's dynamic activation scaling and `modules_to_not_convert` declarations are applied
automatically; `--quant` is not needed for a pre-quantized FP8 repository.

## MoE models and MoQE

MoE (Mixture of Experts) families (DeepSeek V2/V3, GLM-4.7, GLM-4.7-Flash, Phi 3.5 MoE, Qwen3 MoE, Qwen3-VL MoE, Qwen3.5/Qwen3.6 MoE, LFM2/LFM2.5 MoE) support MoQE (Mixture of Quantized Experts): quantizing only the routed experts, which dominate memory, while leaving the rest of the model alone. Enable it when applying ISQ with `--isq-organization moqe`:

```bash
inference run --isq 4 --isq-organization moqe -m Qwen/Qwen3-30B-A3B
```

MoQE also applies when generating UQFF with `inference quantize`. It does not rewrite an already-quantized GGUF or UQFF selected by `--quant`; those weights load as published.

In the Python SDK, pass `organization=t.IsqOrganization.MOQE` inside `t.ModelSelectedPlain(...)` or `t.ModelSelectedMultimodalPlain(...)`, with ISQ set through `t.RuntimeSpec(isq=...)`. Expect small output differences between quantization levels: router decisions are sensitive to numerical noise.

## MLA models (DeepSeek V2/V3, GLM-4.7-Flash)

DeepSeek V2, DeepSeek V3 (including non-distill R1, which uses the V3 architecture), and GLM-4.7-Flash use MLA (Multi-head Latent Attention). The KV cache stores a low-dimensional latent instead of full K/V, so the cache footprint is substantially smaller than standard attention at the same context length.

On CUDA (Unix builds), a specialized MLA decode kernel is used when all of the following hold:

- single-token decode (no attention mask, sequence length 1);
- [paged attention](/guides/perf/paged-attention/) enabled;
- FlashInfer (NVIDIA's attention-kernel library) paged metadata available.

A parallel fast path covers prefill with prefix caching (paged attention on, CUDA device). Otherwise the generic attention path reconstructs the latent per step.

`INFERENCE_RS_NO_MLA=1` forces the generic path; use it when debugging suspected MLA kernel issues, and try `--paged-attn off` as a sanity check for unexpected paged-attention behavior. Background: the [DeepSeek V2 paper](https://arxiv.org/abs/2405.04434).

## GPT-OSS

GPT-OSS experts are stored pre-quantized in MXFP4 (4-bit microscaling float), and its attention uses per-head sinks. Load it without a quantization flag first:

```bash
inference run -m openai/gpt-oss-20b
```

ISQ applies only to the attention layers (and `lm_head`); the expert weights are already quantized.

## Qwen 1

Qwen 1 (`QWenLMHeadModel`, e.g. `Qwen/Qwen-1_8B-Chat`) reads its `qwen.tiktoken` tokenizer when the repository has no `tokenizer.json`, and without a chat template in the repository it uses the ChatML layout of the reference `make_context`, with its default system turn. A safetensors load caps the context at the config's `seq_length`: past it the reference switches on dynamic NTK and logn scaling, which are not implemented. The `qwen` GGUF architecture loads too.

## Qwen3 Next

Qwen3 Next mixes Gated Delta Network (linear attention) layers with full softmax attention, so its cost profile at long contexts differs from a pure softmax model. Qwen3-Coder-Next checkpoints use the same loader.

## Qwen3.5 and Qwen3.6

Qwen3.5 and Qwen3.6 dense and MoE checkpoints are supported. Qwen3.6 shares the Qwen3.5 HF `model_type`, so it loads through the same `Qwen3_5` and `Qwen3_5Moe` paths.

Use nested Hugging Face config overrides to enable YaRN without editing the downloaded checkpoint. This example extends a native 262,144-token Qwen3.5 model to a 1,010,000-token serving limit:

```bash
inference serve -m Qwen/Qwen3.5-27B \
  --hf-overrides '{"text_config":{"rope_parameters":{"rope_type":"yarn","factor":4.0,"original_max_position_embeddings":262144}}}' \
  --max-model-len 1010000
```

Overrides merge recursively, so the checkpoint's `rope_theta`, `partial_rotary_factor`, and MRoPE sections remain intact. `--max-model-len` only sets the prompt-plus-output limit; it does not enable RoPE scaling and cannot exceed the context length supported by the final config. Static YaRN can reduce quality on shorter inputs, so enable it only when the extended context is needed.

## Granite

IBM Granite 4.0 checkpoints (e.g. `ibm-granite/granite-4.0-micro`) mix Mamba-2 recurrent layers with attention layers. The dense Granite 3.x and 4.1 models (`GraniteForCausalLM`, e.g. `ibm-granite/granite-4.1-3b`), Granite MoE (`GraniteMoeForCausalLM`, e.g. `ibm-granite/granite-3.1-1b-a400m-instruct`), Granite MoE with a shared expert (`GraniteMoeSharedForCausalLM`) and the interleaved sliding-window Granite SWA models (`GraniteSWAForCausalLM` and `GraniteMoeSWAForCausalLM`, e.g. `ibm-granite/granite-swash-2b`, with per-head attention sinks) run on the same model with every layer attention. All of them load through auto-detection like any other text model, from safetensors or from llama.cpp's GGUFs. llama.cpp tags the swash tokenizer `granite-docling` and splits it as GPT-2 does, unlike the checkpoint's own tokenizer; a swash GGUF tokenizes as it does in llama.cpp.

Granite 4 Vision (`Granite4VisionForConditionalGeneration`, e.g. `ibm-granite/granite-vision-4.1-4b`) reads images: a SigLIP tower tiled as LLaVA-Next tiles, whose layers feed Window Q-Former projectors that add their features at the image positions before several text layers. `ibm-granite/granite-4.0-3b-vision` ships part of its text weights as a PEFT adapter (`adapter_model.safetensors`), which is folded into them on load as transformers does.

Granite Speech (`GraniteSpeechForConditionalGeneration` and `GraniteSpeechPlusForConditionalGeneration`, e.g. `ibm-granite/granite-speech-4.1-2b`) reads one or more audio clips, resampled to 16 kHz mono, through a Conformer encoder and a windowed Q-Former; each clip takes 3 tokens per 15 encoder frames (0.3 s). Send the audio with a text request such as "can you transcribe the speech into a written format?". Checkpoints that switch a LoRA adapter on for audio (`has_lora_adapter`) are refused.

Both also load from llama.cpp's GGUFs: the text GGUF with its projector (`--mmproj`, an `mmproj-*.gguf` that `convert_hf_to_gguf.py --mmproj` writes), and the original repo for `config.json` and the processor files (`--tok-model-id`):

```bash
inference serve --format gguf -m <dir> -f granite-vision-Q8_0.gguf --mmproj <dir>/mmproj-granite-vision-f16.gguf \
  --tok-model-id ibm-granite/granite-vision-4.1-4b
```

## OLMo

AllenAI's OLMo 1 (`OlmoForCausalLM`, e.g. `allenai/OLMo-1B-0724-hf`), OLMo 2 (`Olmo2ForCausalLM`), Olmo 3 (`Olmo3ForCausalLM`, whose sliding-window layers take plain RoPE beside YaRN full ones) and OLMoE (`OlmoeForCausalLM`) load through auto-detection, from safetensors or from llama.cpp's GGUFs (`olmo`, `olmo2`, `olmoe`). The original pre-HF OLMo 1 checkpoints (`OLMoForCausalLM`, `model.transformer.blocks.*`) are not supported; use their `-hf` conversions.

## LFM2 and LFM2.5

LiquidAI LFM2 and LFM2.5 dense and MoE checkpoints are supported. LFM2-VL and LFM2.5-VL are supported for image input.

The official repos ship `chat_template.jinja`, including the Liquid tool-call format. It is auto-detected like other model-native tool-call formats.

## Gemma

Gemma repos are gated: accept the license on the Hugging Face model page, then authenticate with `inference login`.

Gemma 4 accepts image, audio, and video parts mixed in one message, and enforces its tool-call format through constrained decoding by default; see [tool calling](/guides/agents/tool-calling-basics/).

## Muse Glimmer

Muse Glimmer loads through normal model auto-detection:

```bash
inference run -m meta-models/Muse-Glimmer-30B
```

The native safetensors checkpoint accepts text, images, and video; it does not accept audio. Video is represented as timestamped frame groups, and the model card notes that the model was trained primarily for image rather than video understanding.

The model's ATEM chat template is detected automatically. Tool calling supports automatic, required, named, and parallel calls through the same HTTP, Python, Rust, and agent APIs as other tool-capable models. Muse reads the `reasoning_strength` template variable, so inference.rs maps the public `reasoning_effort` control to it. The published Muse tiers are `low`, `medium`, `high`, and `xhigh`; omission uses the template's `high` default.

ISQ, UQFF, paged attention, prefix caching, tensor parallelism, and text-backbone LoRA use the standard multimodal model paths. For GGUF-specific requirements and its image-only projector limitation, see [GGUF compatibility](/reference/gguf-support/).

## MatFormer

MatFormer-trained models encode multiple model sizes in one checkpoint; the desired slice is selected at load time with two values:

- `matformer_config_path`: path to the slice config file (CSV or JSON) shipped with the model card.
- `matformer_slice_name`: the named slice within that file.

Without these, the default (full) configuration loads. Gemma 3n (`google/gemma-3n-E4B-it`) is the MatFormer model in the supported list; the bundled `configs/matformer_configs/gemma3n.csv` contains the full E4B configuration, the official E2B slice, and intermediate E1.96B-E3.79B slices:

```bash
inference run -m google/gemma-3n-E4B-it \
  --matformer-config-path configs/matformer_configs/gemma3n.csv \
  --matformer-slice-name "Config for E2.49B (block-level)"
```

The same slice selection is available on every surface:

- CLI: `--matformer-config-path` / `--matformer-slice-name` on `run`, `serve`, and `bench`.
- TOML configs: `matformer_config_path` / `matformer_slice_name`.
- Python: `matformer_config_path` / `matformer_slice_name` on `t.ModelSelectedMultimodalPlain` and the other model selectors that carry them.
- Rust SDK: `with_matformer_config_path` / `with_matformer_slice_name` on the model builders.

Use the full configuration for quality and smaller slices for constrained devices.

## Mistral Small tool calling

Mistral Small 3 checkpoints can do tool calling, but some repos do not ship the right chat template. Use the bundled one:

```bash
inference serve --quant 4 \
  --jinja-explicit chat_templates/mistral_small_tool_call.jinja \
  -m mistralai/Mistral-Small-3.2-24B-Instruct-2506
```

## LLaVA chat templates

Mistral-backed LLaVA checkpoints work with the default template. Vicuna-backed checkpoints need the Vicuna template:

```bash
inference run -m llava-hf/llava-v1.6-vicuna-7b-hf \
  -c chat_templates/vicuna.json --image photo.jpg -i "Describe this image"
```

## Qwen3-VL

Per-request video frame-sampling overrides are not exposed. In multi-turn conversations reusing prefix cache entries, pixel inputs are narrowed per turn by grid count, not image count.

## Qwen3-ASR

Qwen3-ASR (`Qwen3ASRForConditionalGeneration`, e.g. `Qwen/Qwen3-ASR-1.7B`) transcribes audio clips, resampled to 16 kHz mono, through the AuT encoder in front of a Qwen3 decoder; each second of audio takes 13 tokens, and the encoder attends within 8 s windows. It serves `/v1/audio/transcriptions` (see the [speech models guide](/guides/models/use-speech-models/)) and chat requests, where the model answers `language <name><asr_text><transcript>`. Both the original repos (`thinker.*` weights) and the transformers `-hf` conversions load.

It also loads from llama.cpp's GGUFs (a `qwen3vl` text GGUF with its `qwen3a` projector), with the original repo for `config.json` (`--tok-model-id`). The original repo has no `tokenizer.json` or chat template; the GGUF provides both:

```bash
inference serve --format gguf -m <dir> -f Qwen3-ASR-1.7B-Q8_0.gguf --mmproj <dir>/mmproj-Qwen3-ASR-1.7B-Q8_0.gguf \
  --tok-model-id Qwen/Qwen3-ASR-1.7B
```

## Voxtral

Voxtral Mini and Small (`VoxtralForConditionalGeneration`, e.g. `mistralai/Voxtral-Mini-3B-2507`) answer questions about audio clips in chat: the Whisper encoder reads each clip, resampled to 16 kHz mono and padded to whole 30 s chunks, and every chunk takes 375 `[AUDIO]` tokens at the start of the user turn. It also serves `/v1/audio/transcriptions` in its transcription mode (`lang:<code>[TRANSCRIBE]`, as mistral_common encodes it), for English, Spanish, French, Portuguese, Hindi, German, Dutch and Italian, or with no language given. The repos ship both transformers weights (`config.json`, `model-*.safetensors`) and Mistral's native ones (`params.json`, `consolidated.safetensors`); the transformers pair loads. The repos have no chat template, so the loader applies mistral_common's layout (`[SYSTEM_PROMPT]...[/SYSTEM_PROMPT][INST]...[/INST]`, no spaces).

It also loads from llama.cpp's GGUFs (a `llama` text GGUF with its `voxtral` projector) with nothing else: the config comes from the GGUFs' metadata, and the loader's template replaces the one the published GGUFs embed (another Mistral model's, with an agent system prompt):

```bash
inference serve --format gguf -m <dir> -f Voxtral-Mini-3B-2507-Q4_K_M.gguf
```

Voxtral Realtime (`VoxtralRealtimeForConditionalGeneration`) is a different, streaming transcription model; see the [speech models guide](/guides/models/use-speech-models/).

## GLM-ASR

GLM-ASR (`GlmAsrForConditionalGeneration`, e.g. `zai-org/GLM-ASR-Nano-2512`) transcribes Chinese and English through `/v1/audio/transcriptions` (with the reference processor's prompt; a `language` is ignored, since the model takes none) and answers questions about audio in chat. Each clip, resampled to 16 kHz mono, is cut into 30 s windows, up to 655 s; every whole window takes 375 tokens.

## Ultravox

Ultravox (e.g. `fixie-ai/ultravox-v0_5-llama-3_2-1b`) answers questions about audio clips in chat. Its safetensors repos hold only the audio tower and projector (the text model is another repository), so it loads from llama.cpp's GGUFs, a `llama` text GGUF with its `ultravox` projector, with nothing else:

```bash
inference serve --format gguf -m <dir> -f Llama-3.2-1B-Instruct-Q8_0.gguf
```

Each clip, resampled to 16 kHz mono, is read in 30 s chunks with no length limit and takes one token per 160 ms of real audio, at the start of the user turn. There is no transcription mode.

## Audio Flamingo 3

Audio Flamingo 3 (`AudioFlamingo3ForConditionalGeneration`, e.g. `nvidia/audio-flamingo-3-hf`) answers questions about speech, sounds and music in chat and transcribes through `/v1/audio/transcriptions` (with the reference processor's prompt; a `language` is ignored). Each clip, resampled to 16 kHz mono, is cut into 30 s windows, up to 600 s; every whole window takes 750 tokens. Its repo holds the weights twice (sharded and as one file); the sharded files are what load. The weights are under the NVIDIA OneWay Noncommercial licence.

## Qwen2-Audio

Qwen2-Audio (`Qwen2AudioForConditionalGeneration`, e.g. `Qwen/Qwen2-Audio-7B-Instruct`) answers questions about audio clips in chat. Each clip, resampled to 16 kHz mono, is read as one 30 s window (a longer clip is cut to its first 30 s, as the reference processor does) and takes one token per 40 ms of real audio, on its own `Audio N:` line before the text. The checkpoint's generation config sets a repetition penalty of 1.1, which applies unless a request sets its own.

## Llama 4

Llama 4 Scout supports up to 10M tokens of context. Using the full window requires paged attention with a large memory budget, generally with multi-GPU tensor parallelism.

## Multimodal device mapping

For most multimodal models the text backbone holds most of the parameters, so device mapping and topology apply mainly to the text portion; the vision, audio, or video encoder stays on its supported device path.

## Phi

Phi 3.5 Vision works best with a single image; multiple images are resized together. Phi 4 Multimodal accepts audio and image parts in the same message. Phi 3.5 MoE has 16 experts and routes each token to 2 of them; it benefits from [MoQE](#moe-models-and-moqe).
