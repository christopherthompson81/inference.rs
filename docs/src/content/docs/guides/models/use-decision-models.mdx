---
title: Use decision models
description: Answer typed questions about text (choose an option, score on a scale, decide whether a statement holds) in one forward pass, with calibrated probabilities.
---

A decision model reads a **state** (a message, a ticket, a document, any JSON) and answers **typed questions** about it, one forward pass per question and no generated text. Each answer comes with probabilities over its options, so routing, triage, moderation and scoring code can act on them directly, without parsing model output.

## Loading a decision model

These checkpoints load by their file layout (an `encoder/` folder, a `tokenizer/` folder and the model's own config beside the weights), so they need no `--arch`:

- `convaiinnovations/laya`: ModernBERT-large with a two-block decision head, 512-token inputs, temperatures fitted per question type and option count.
- `SupersonicLabs/Julia-1`: mmBERT-small (multilingual) with the same head, inputs up to 8192 tokens, uncalibrated.

```bash
inference serve -m convaiinnovations/laya
```

laya's `multilingual/` and `typed-decisions/` variants load from a local copy of their folder.

### Chat models with a decision profile

Some decision models are chat models fine-tuned to answer with the code of an option. Their GGUFs, as llama.cpp's converter writes them, carry a decision profile: `<arch>.decision.type`, a `systemone` chat template that renders a question as a prompt, and temperatures. Such a GGUF loads like any other, and `/v1/decisions` then renders each question with that template and reads the next-token logits of one label token per option (no text is generated). These types are supported: `nimble`, `openjev`, `lev`, `pplx-decider`, `vllm-d3`, `h2o-lightning`, `lfm2-d1`, `kev`, `clef` and `vllm-decision2`.

```bash
inference serve --format gguf -m <repo or folder> -f <file>.gguf
```

`pplx-decider` and `vllm-d3` (Qwen3.5 checkpoints) read their prompt with non-causal full attention: the whole prompt runs in one pass, and the server keeps no prefix cache for such a model.

`kev` (Qwen3.5, e.g. `ggml-org/Kev-4B-GGUF`) scores options with a pointer head instead of labels: each option in its prompt ends with a `<|box_end|>` token, and an option's score is the dot product of the last token's query with that token's key, both projected from the hidden states. The head takes the place of the model's vocabulary output, so a kev model answers decisions only and refuses chat and completion requests.

`h2o-lightning` reads its labels from the GGUF and relaxes the request: a question may leave out its `type` (a `choice`) and its `instructions`, a `score` may have a single level, and a `noul` may describe its sides under `yes` and `no`. A state longer than 32000 tokens keeps its first and last 16000 around a `...` line. `vllm-d3` also accepts a question without instructions.

`lfm2-d1` chooses each question's labels from its type and keys (a choice's single-letter keys, else `A`, `B`, ...; a score's level digits; `yes` / `no` for a noul) and scores each by its best spelling. It and `vllm-d3` accept a null `state`.

`clef` (its own `clef` architecture over Qwen3.5) decides every question of a request together: one prompt lists them all, and a joint head scores each option from the question and option spans of that prompt. Like `kev`, it answers decisions only.

`vllm-decision2` (its own architecture over Qwen3) scores each question in its own prompt with an option head at the end of each option and of the question, and checks requests as its reference does (a state, instructions and descriptions that are text, an object or an array; at least two choice options). Load it from llama.cpp's conversion of the safetensors checkpoint (`convert_hf_to_gguf.py`): the GGUFs vllm-sr publishes use another layout, which llama.cpp does not load either. Like `kev` and `clef`, it answers decisions only.

The other llama.cpp decision types (`granite-switch`, `lfm2-d1-omni`) are not supported, and no decision type takes images yet.

## Asking questions

`POST /v1/decisions` takes a `state` and `questions`, a map of question ids to questions. The request and answer follow TypeSafe's System One API, which `/v1/systemone` also serves, so a client of that API (or of llama.cpp's server, or laya's own) only changes its base URL.

```bash
curl http://localhost:1234/v1/decisions \
  -H "Content-Type: application/json" \
  -d '{
    "state": "Customer message: I was charged twice for my order last week and nobody has replied.",
    "questions": {
      "route": {"type": "choice", "instructions": "Which team should handle this?",
                "criteria": {"billing": null, "shipping": null, "technical": null}},
      "angry": {"type": "noul", "instructions": "Is the customer angry?"},
      "urgency": {"type": "score", "instructions": "How urgent is this?",
                  "criteria": ["can wait", "this week", "today", "right now"]}
    }
  }'
```

Each question has a `type`, its `instructions` (text, or any JSON value), and `criteria` whose shape the type sets:

- `choice`: an object mapping each option (2 to 255) to its description, or `null`. An array of option names works too.
- `score`: an array of 2 to 10 level descriptions, lowest level first.
- `noul`: optional; an object with descriptions of `true` and `false`.

A `state` that is not a string reaches the model as JSON text. Questions are answered independently, and a request's questions batch together.

## Answers

`answers` maps each question id to its answer, in the request's order:

- `choice`: `choice` (the most probable option), `probabilities` (one per option, summing to 1) and `confidence` (from 0, every option equally likely, to 1). laya and Julia-1 report one minus the normalized entropy; the chat models TypeSafe's formulas, `(p_max - 1/k) / (1 - 1/k)` for a choice and, for a score, one minus the mean distance to the most probable level relative to a uniform distribution's.
- `score`: `score` (the expected level index, which can fall between two levels), `legend` (each level's description), `probabilities` and `confidence`.
- `noul`: `noul`, the probability that the statement holds.

`usage.input_tokens` counts every question's prompt tokens; `output_tokens` is always 0.

The probabilities are scaled by the temperatures the checkpoint ships (laya fits them per question type and option count); they are not guaranteed to be calibrated for your data. A chat model reads at most as many options as it has single-token labels (52 for openjev, up to 255 for the others). Long questions and options are cut to the model's budget for them (192 tokens for laya, 256 for Julia-1), and a long state to what the rest of the input leaves; a question whose options cannot all fit is refused.

The Rust SDK has `model.decide(request)`, the Python SDK `engine.decide(...)`, the C# binding `Decide(...)`, and the C ABI `inference_decide`.
