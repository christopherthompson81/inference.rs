inference.rs serves diffusion models through `POST /v1/images/generations`: FLUX and HiDream-O1-Image; see the [supported models reference](/reference/supported-models/).

## Running FLUX

```bash
inference serve -m black-forest-labs/FLUX.1-schnell
```

`FLUX.1-schnell` is permissively licensed. `FLUX.1-dev` requires Hugging Face license acceptance: accept on the model page, then authenticate with `inference login`.

A FLUX repo auto-detects as the fully-resident `Flux` path. To trade speed for a much smaller GPU footprint, use the `FluxOffloaded` loader: `inference serve diffusion -m <repo> --diffusion-arch flux-offloaded`, or from the Python and Rust SDKs shown below:

| Loader | GPU footprint | Notes |
|---|---|---|
| `Flux` | Full model resident | Fully loaded path. Fastest. |
| `FluxOffloaded` | Much smaller | Offloads components to CPU; useful when the full model does not fit. |

### From GGUF files

A local directory in the single-file layout loads FLUX from GGUF, with the T5 text encoder quantized too:

| File | What it is |
|---|---|
| `flux1-dev-Q8_0.gguf` (or `flux1-schnell-*.gguf`) | The FLUX transformer, quantized |
| `ae.safetensors` | The FLUX autoencoder |
| `t5-v1_1-xxl-encoder-*.gguf` (optional) | The T5-XXL text encoder, quantized, in llama.cpp naming |
| `clip_l.safetensors` (optional) | The CLIP-L text encoder |

```bash
inference serve -m /path/to/flux-files
```

The directory needs exactly one `flux<N>-dev*.gguf` or `flux<N>-schnell*.gguf` and at most one `t5*.gguf`. The
transformer config is read off the GGUF's tensors. The T5 and CLIP configs and tokenizers, and any text encoder missing from the directory, come from the Hugging
Face Hub. FLUX.1-dev at Q8_0 with a Q8_0 T5 needs roughly 18 GB of GPU memory; quantized weights cannot be offloaded,
so the GGUF layout loads with `Flux`, not `FluxOffloaded`.

## Running HiDream-O1-Image

```bash
inference serve -m HiDream-ai/HiDream-O1-Image-Dev
```

HiDream-O1-Image is one 8B Qwen3-VL transformer that reads the prompt and denoises the image's RGB pixels directly,
in 32-pixel patches, with no separate text encoder or VAE. Both checkpoints load from their Hugging Face repos:

| Checkpoint | Loader | Sampling |
|---|---|---|
| `HiDream-ai/HiDream-O1-Image` | `hidream-o1` | 50 UniPC steps with classifier-free guidance 5.0 (two forwards a step); `steps` and `guidance_scale` override them |
| `HiDream-ai/HiDream-O1-Image-Dev` | `hidream-o1-dev` | Distilled: its fixed 28-step schedule, no guidance; a `steps` other than 28 or a `guidance_scale` above 1 is refused |

The two repos have the same config and file layout, so the variant comes from the name: a model id whose last
part contains `-dev` (any case), or a hub cache snapshot of such a repo, loads as Dev, and anything else as the full
model. This detection belongs to plain `inference serve -m <repo>`: the `serve diffusion` subcommand defaults to
FLUX, so it needs the architecture named, as in `inference serve diffusion -m <dir> --diffusion-arch hidream-o1-dev`;
the SDKs take the loader type. The repos store F32 weights (35 GB); they load
in BF16 by default, about 18 GB of GPU memory.

The model generates at its trained resolutions only, about 4.2 megapixels each: a request's `width` and `height`
snap to the one of 2048x2048, 2304x1728, 2560x1440, 2496x1664, 3104x1312, 2304x1792 (or their portrait forms)
with the closest aspect ratio, and the response image has that size. Image editing and subject references
(conditioning on input images) are not supported yet.

## Generating an image

<Tabs>
<TabItem label="HTTP">

```bash
curl http://localhost:1234/v1/images/generations \
  -H "Content-Type: application/json" \
  -d '{
    "model": "default",
    "prompt": "A photograph of a golden retriever wearing a scarf in autumn leaves.",
    "n": 1,
    "height": 1024,
    "width": 1024
  }'
```

The response is JSON with a `data` array. Each entry has either `url` or `b64_json`, controlled by `response_format` (default `url`); see [Request fields](#request-fields) and [Output handling](#output-handling).

</TabItem>
<TabItem label="Python">

```python
import inference_rs as ir
from inference_rs import types as t

spec = t.EngineSpec(
    model=t.ModelSelectedDiffusionPlain(
        model_id="black-forest-labs/FLUX.1-schnell",
        arch=t.DiffusionLoaderType.FLUX_OFFLOADED,
    )
)

with ir.Engine(spec) as engine:
    response = engine.image_generation(
        t.ImageGenerationRequest(
            prompt="A vibrant sunset in the mountains, high quality.",
            response_format=t.ImageGenerationResponseFormat.URL,
        )
    )
    print(response.data[0].url)
```

</TabItem>
<TabItem label="Rust">

```rust
use inference::{DiffusionLoaderType, DiffusionModelBuilder, ImageGenerationRequest};

let model = DiffusionModelBuilder::new(
    "black-forest-labs/FLUX.1-schnell",
    DiffusionLoaderType::FluxOffloaded,
)
.build()
.await?;

let response = model
    .generate_image(ImageGenerationRequest {
        seed: Some(7),
        ..ImageGenerationRequest::new("A vibrant sunset in the mountains, high quality.")
    })
    .await?;
println!("{}", response.data[0].url.as_ref().unwrap());
```

</TabItem>
</Tabs>

## Request fields

| Field | Default | Notes |
|---|---|---|
| `prompt` | required | Text prompt. |
| `n` | 1 | Number of images, 1 to 10. |
| `height` | 720 | Output height in pixels. |
| `width` | 1280 | Output width in pixels. |
| `response_format` | `"url"` | `"url"` (response carries the path that serves the PNG from the file store in `url`) or `"b64_json"` (response carries the base64-encoded PNG in `b64_json`). |
| `steps` | the model's | Denoising steps, 1 to 1000. An inference.rs extension. |
| `guidance_scale` | the model's | Guidance scale: FLUX.1-dev's distilled guidance, HiDream-O1-Image's classifier-free guidance. An inference.rs extension. |
| `seed` | random | Seeds the noise: the same request and seed give the same image on the same device and dtype; with `n` above 1, choice `i` takes `seed + i`. An inference.rs extension. |

`size` (the OpenAI string form) is not supported. Use `height` and `width`.

## Memory notes

FLUX is memory-hungry at native precision: the model is roughly 12B parameters, and the T5 XXL text encoder adds a large memory footprint. For low-memory hosts, use the `FluxOffloaded` loader from the [Running FLUX](#running-flux) table.

For a smaller footprint without offloading, load FLUX and T5 from GGUF ([From GGUF files](#from-gguf-files)).

HiDream-O1-Image in BF16 needs about 18 GB of GPU memory for its weights.

Diffusion models do not support [ISQ (in-situ quantization)](/reference/quantization-types/). Load them at native precision instead of passing `--quant` or `--isq`; they are generally more sensitive to quantization than language models.

## Output handling

With `url` (the default), the PNG goes into the engine's [file store](/reference/http-api/) and `url` is the path that
serves it, `/v1/files/<id>/content`, including any prefix the router is nested under. Like other stored files it
expires after 30 minutes, or sooner if the model is unloaded, the server restarts, or newer files push the
model's store past its 1 GiB cap. Use `b64_json` to keep an image out of the store. Over HTTP, fetch it from the server; through the Python SDK or the C ABI, read it by id:

```bash
curl -o out.png http://localhost:1234/v1/files/<id>/content
```

```python
file_id = response.data[0].url.split("/")[-2]
with open("out.png", "wb") as f:
    f.write(engine.file_content(file_id).data)
```

The Rust SDK keeps the image in the same store; read it by id through the model, which derefs to the engine:

```rust
let url = response.data[0].url.as_deref().unwrap();
let file_id = url.rsplit('/').nth(1).unwrap();
std::fs::write("out.png", model.file_content(file_id)?.bytes)?;
```

With `b64_json`, `b64_json` is the base64-encoded PNG, as in OpenAI's API:

```python
import base64

with open("out.png", "wb") as f:
    f.write(base64.b64decode(response.data[0].b64_json))
```
