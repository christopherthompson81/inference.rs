A handful of flags control how many requests run at once and how much repeated work the engine can skip. The defaults are reasonable for a single-user server; tune them when traffic is concurrent or shares long prompts.

```bash
inference serve -m Qwen/Qwen3-4B \
  --max-seqs 64 \
  --max-num-batched-tokens 4096 \
  --max-prefill-chunk-tokens 512 \
  --pa-memory-fraction 0.9
```

`--pa-memory-fraction` sizes the [paged attention](/guides/perf/paged-attention/) block pool; see [When paged attention matters](#when-paged-attention-matters) below.

Use `inference bench -m <model>` for single-request kernel measurements. For server tuning, replay
the same prompt and output lengths through the HTTP API at the production concurrency; flags that
help one workload can hurt another.

## Concurrency: max running sequences

Cap the number of sequences running at once. Waiting requests queue until a slot frees. Raise it for high-concurrency serving; lower it to bound per-request latency or memory.

<Tabs>
<TabItem label="CLI">

```bash
inference serve -m Qwen/Qwen3-4B --max-seqs 64
```

</TabItem>
<TabItem label="Python">

```python
import inference_rs as ir
from inference_rs import types as t

spec = t.EngineSpec(
    model=t.ModelSelectedPlain(model_id="Qwen/Qwen3-4B"),
    runtime=t.RuntimeSpec(max_seqs=64),
)
engine = ir.Engine(spec)
```

</TabItem>
<TabItem label="Rust">

    .build()
    .await?;

The default is the same on every surface:

| Surface | Flag / argument | Default |
|---|---|---|
| CLI | `--max-seqs` | 4 |
| Python | `t.RuntimeSpec(max_seqs=...)` | 4 |
| Rust | `.with_max_num_seqs(...)` | 4 |

The default is low because each running sequence holds memory for as long as it runs, whether or not the server is busy: a hybrid model's recurrent state alone is about 150 MB per sequence at 27B, so 32 sequences would take 5 GB. Raise it for a server many clients share. A model can set its own: `max_seqs` in a model spec, a `[[models]]` entry, or a model manager load (the web UI's **Sequences** field).

More running sequences need more KV cache. With paged attention, size the block pool to match: one of `--pa-context-len`, `--pa-memory-mb`, or `--pa-memory-fraction` (default: one sequence at the model's full context). If the pool runs out of blocks mid-generation, the scheduler preempts a running sequence, frees its blocks, and requeues it, which costs recomputation.

## Mixed prefill and decode

Three limits control how new prompts share the GPU with active decodes:

- `--max-num-batched-tokens` bounds the total token work in a scheduler batch (default 4096).
- `--max-prefill-chunk-tokens` bounds each chunkable CUDA text-prompt scheduling quantum (default
  512). The budget is divided across admitted prompt sequences, limiting how long active decodes
  wait behind one non-preemptible prefill step. Raw-logit, adapter, and multimodal prompt paths that
  cannot be split remain atomic; the limit does not change CPU or Metal scheduling.
- `--max-decode-steps-before-prefill` bounds how long a waiting prompt can be deferred while a
  decode batch is active (default 8). Raise it to favor inter-token latency for active requests;
  lower it to reduce time to first token under sustained arrivals.

Measure both output throughput and latency percentiles when changing these values. A larger prefill
chunk can improve prefill throughput while increasing decode latency, especially for long prompts.

## When paged attention matters

Concurrency beyond a few sequences is the main reason to care about paged attention. It is the difference between per-sequence contiguous caches sized for the maximum context and a shared block pool with a fixed budget:

- With paged attention (default on CUDA): continuous batching against the block pool, block-level prefix sharing, and the CUDA decode-graph and paged flash attention (fattn) fast paths.
- Without it (Metal, CPU, or `--paged-attn off`): the default scheduler is first-come-first-served and batches running sequences by equal length; sequences at other lengths wait their turn and accumulate priority.

## Prefix caching

Prefix caching skips prefill for tokens the engine has already processed, which is most valuable for multi-turn chat and shared system prompts.

`--prefix-cache-n` sets how many cached prefixes stay on device (default 16, `0` disables). `--no-kv-cache` disables the KV cache entirely and prefix caching with it.

<Tabs>
<TabItem label="CLI">

```bash
inference serve -m Qwen/Qwen3-4B --prefix-cache-n 32
```

</TabItem>
<TabItem label="Python">

```python
import inference_rs as ir
from inference_rs import types as t

spec = t.EngineSpec(
    model=t.ModelSelectedPlain(model_id="Qwen/Qwen3-4B"),
    runtime=t.RuntimeSpec(prefix_cache_n=32, no_kv_cache=False),
)
engine = ir.Engine(spec)
```

</TabItem>
<TabItem label="Rust">

```rust
let model = inference::ModelBuilder::new("Qwen/Qwen3-4B")
    .with_prefix_cache_n(Some(32))
    .build()
    .await?;
```

`.with_no_kv_cache()` disables the KV cache (and prefix caching with it).

</TabItem>
</Tabs>

The mechanism depends on the attention mode:

- Paged attention: sequences sharing a token prefix reuse the same reference-counted cache blocks; matching blocks of a new request are not recomputed.
- Non-paged: completed sequences' caches are kept whole; a new request whose tokens extend a cached sequence resumes from it. Beyond `--prefix-cache-n` device entries, the oldest caches are evicted (dropped, not offloaded); a later matching request re-prefills.

On hybrid models (Qwen3.5, Qwen3.8), a prefix resumes only at a saved recurrent-state snapshot. After each reply, while nothing else waits, the engine prefills the reply on top of its prompt's snapshot, so the next turn (an agent's prompt, reply and tool result) resumes after the reply and computes only what is new.

### Keeping prefixes in host memory or on disk

Long sessions, such as agent loops that resend their whole history each turn, lose their cached prefix when it is evicted or the server restarts, and the next request re-prefills everything: about 23 s for 28K tokens of Qwen3.8 27B on an RTX 3090. `--prefix-cache-dir` writes each cached prefix through to a directory as it is taken, and restores it into GPU memory when a later request starts with it (0.23 s for those 28K tokens):

```bash
inference serve -m <model> --prefix-cache-dir ~/.cache/inference-rs/prefix-cache --prefix-cache-disk-gib 64
```

- Hybrid models (Qwen3.5 and Qwen3.8's linear-attention layers) on CUDA with paged attention, text prompts; a DFlash drafter's own state is stored with each prefix.
- Each 32-token block is stored once and shared by every prefix that contains it, so a growing conversation writes only its new blocks.
- Entries are kept apart per model setup (weights, dtype, KV cache type and layout, drafter), and each block's tokens are checked on restore. When a release changes what a model stores in its cache, the directory's older entries are removed on startup rather than restored.
- An entry expires an hour after its last use (`--prefix-cache-disk-ttl-mins`), and a request can name its own lifetime: an Anthropic `cache_control` breakpoint on `/v1/messages` keeps its prefix five minutes, or its `ttl` (`"1h"`); `prefix_cache_ttl_secs` does the same on `/v1/chat/completions`. The longest breakpoint in a request wins, and each hit restarts the clock. Expired entries go within a minute, and on startup.
- `--prefix-cache-disk-gib` (default 64) caps the directory; past it, the least recently used prefixes go first.
- The operating system's page cache keeps recently used entries in RAM, so a restore after a short pause usually reads no disk at all.
- `--prefix-cache-ram-gib` keeps entries in host memory, under the same block sharing, checks and lifetimes. With a directory it sits in front: each prefix goes to both, a restore reads memory first, and a prefix restored from disk is copied back into memory. Without one the cache lives in memory alone and leaves no files, for machines with more RAM than disk to spare; it does not survive a restart.
- With either tier a DFlash drafter keeps its state for only two prefixes on the GPU (instead of one per cached prefix, about 50 MB each for Qwen3.6 35B-A3B), and the rest restore from the host: on a 24 GB card that is tens of thousands more tokens of context.
- In Python set `RuntimeSpec(prefix_cache_dir=..., prefix_cache_disk_gib=..., prefix_cache_ram_gib=..., prefix_cache_disk_ttl_mins=...)`; in Rust `.with_prefix_cache_dir(dir, Some(gib))` and `.with_prefix_cache_ram(gib)`.

## Memory planning for automatic device mapping

Automatic device mapping reserves activation and KV memory for a worst case you declare: `--max-seq-len` (default 4096) and `--max-batch-size` (default 1). If you expect long prompts or large batches, raise these so layers are not placed too greedily; if memory is tight, the defaults already keep reservations small. See [distributed inference](/guides/perf/distributed-inference/) for manual placement.

## CPU threads and affinity

CPU inference uses Candle's thread pools. On Linux systems that expose heterogeneous CPU capacity through sysfs, inference.rs defaults the CPU worker count to the high-capacity cores. On homogeneous systems it falls back to the physical core count.

Set `RAYON_NUM_THREADS` or `CANDLE_NUM_THREADS` to override the worker count:

```bash
CANDLE_NUM_THREADS=10 inference bench --cpu -m meta-llama/Llama-3.2-3B-Instruct
```

For CPU affinity on Linux, use `CANDLE_CPU_MASK` with cpulist syntax. When no thread-count env var is set, the mask size also becomes the default worker count:

```bash
CANDLE_CPU_MASK=15-19 inference bench --cpu -m meta-llama/Llama-3.2-3B-Instruct
CANDLE_CPU_MASK=5-9,15-19 inference serve --cpu -m meta-llama/Llama-3.2-3B-Instruct
```

Hard affinity is not enabled by default because it can help one CPU/model pair and hurt another. To try the automatic high-capacity CPU mask without spelling out a list, set `CANDLE_CPU_AFFINITY=1`. The full list is in the [environment variables reference](/reference/environment-variables/#cpu-runtime).

## CUDA defaults worth knowing

On CUDA, two decode fast paths are on by default and need no tuning: the HND-layout paged cache (decoded by fattn) and CUDA decode graphs. Graphs have an env-var switch (`INFERENCE_RS_CUDA_GRAPHS`) only for debugging and benchmarking comparisons; details on the [paged attention page](/guides/perf/paged-attention/).

Quantization is the other big throughput lever, traded against quality: see [quantize a model](/guides/quantization/quantize-a-model/).
