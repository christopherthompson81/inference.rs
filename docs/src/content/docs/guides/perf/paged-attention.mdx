Standard attention allocates one contiguous KV cache per sequence, sized for the maximum context length. Paged attention splits the cache into fixed-size blocks and allocates them on demand from a central pool, so many concurrent sequences share a predictable VRAM budget.

<Tabs>
<TabItem label="CLI">

```bash
# Force on, with a specific KV cache memory budget in MB
inference serve --paged-attn on --pa-memory-mb 8192 -m Qwen/Qwen3-4B

# Force off
inference serve --paged-attn off -m Qwen/Qwen3-4B
```

`--paged-attn` accepts `auto` (default), `on`, or `off`. `auto` enables paged attention on CUDA and disables it on Metal and CPU.

</TabItem>
<TabItem label="Python">

```python
import inference_rs as ir
from inference_rs import types as t

spec = t.EngineSpec(
    model=t.ModelSelectedPlain(model_id="Qwen/Qwen3-4B"),
    runtime=t.RuntimeSpec(
        paged_attn=True,
        paged_cache=t.PagedCacheSpec(context_len=1024, block_size=32),
    ),
)
engine = ir.Engine(spec)
```

`paged_attn=True` forces it on, `False` forces it off, and leaving it unset picks the device default. `t.PagedCacheSpec` mirrors the `--pa-*` flags: at most one of `context_len`, `memory_mb` or `memory_fraction` sizes the pool, and `block_size` and `cache_type` tune the cache. [Full example](/examples/python/paged-attention/).

Use paged attention when:

- Serving more than a handful of concurrent requests.
- Predictable VRAM usage is required.
- Running long-context models (32k+) where standard caches would be enormous.
- Using CUDA decode graphs (see below).

## Memory budget

The pool's size is set via one of three mutually exclusive flags:

- `--pa-memory-mb <mb>`: KV cache budget in MB.
- `--pa-memory-fraction <f>`: KV cache budget as a fraction of VRAM.
- `--pa-context-len <n>`: allocate KV cache sized for this context length.

When none are set, the pool holds one sequence at the model's full context (its window, or `--max-model-len`), or what is free when that is less, so several models can share a GPU. `--pa-memory-fraction 0.9` gives a lone model most of the free VRAM for more concurrent sequences.

Two more flags tune the cache itself:

- `--pa-block-size <n>`: block size (default 32).
- `--pa-cache-type`: KV cache storage: `auto` (the model's dtype, or `q3` when that buys GPU room for [offloaded MoE experts](/guides/perf/moe-expert-offload/)), `none` (the model's dtype, always), `f8e4m3`, `q2`..`q8` (K and V at that many bits), or `qK/qV` such as `q8/q4` (see [KV cache quantization](#kv-cache-quantization)). This is separate from model-weight quantization (`--quant`/`--isq`); the two are chosen independently. A model loaded through the model manager (the web UI) can set its own with `paged_cache_type`.

Scheduler memory and latency are controlled independently:

- `--max-num-batched-tokens <n>`: total scheduler-step token budget (default 4096).
- `--max-prefill-chunk-tokens <n>`: batch-wide chunkable CUDA text-prompt quantum (default 512).
- `--max-decode-steps-before-prefill <n>`: maximum decode turns before a waiting prompt receives service (default 8).

See the [serve flag reference](/reference/cli/serve/) for all `--pa-*` flags.

Raw-logit, adapter, and multimodal prompt paths that cannot be split remain atomic. The prefill
chunk limit does not change CPU or Metal scheduling.

## How it works

The default block size is 32 tokens. Supported block sizes are 8, 16, and 32; other values fail to load, since Metal's paged kernel dispatches on block size explicitly and fattn's paged path needs a power of two.

Each sequence holds a list of block pointers. On each decoding step, the scheduler checks whether the sequence has a free slot in its tail block; if not, it allocates a new block from the pool. When a sequence finishes, its blocks return to the pool.

Sequences that begin with identical tokens share the blocks holding those tokens. A shared block is reference-counted rather than duplicated. This is the mechanism behind [prefix caching](/guides/perf/throughput-tuning/) when paged attention is on.

MLA (Multi-head Latent Attention)'s latent cache is supported through a dedicated kernel path. On CUDA, other layers (with equal K and V head dims) use the HND cache layout (named for FlashInfer, NVIDIA's attention-kernel library; see [Flash attention vs FlashInfer](#flash-attention-vs-flashinfer) below); Metal and CPU use the Standard layout.

## CUDA fast paths

On CUDA, paged attention dispatches to one of two paths:

- Default decode and eligible prefill chunks: fattn (llama.cpp's FlashAttention kernels) reading the HND-layout paged cache in place. This covers compute capability 7.5+ (Turing and newer), head dims 64, 80, 96, 112, 128 and 256 (and 512 with grouped-query attention), and FP16, BF16, FP8 or quantized caches, including sliding windows, attention sinks (gpt-oss) and chunked attention (Llama 4).
- Fallback: anything else (older GPUs, other head dims, FP32 caches) gathers each sequence's blocks and then runs the available attention backend. It is slower, and decode over the gather runs without CUDA graphs.

CUDA prompts are chunked from the batch-wide token budget. The per-sequence chunk is the budget
divided by the admitted prompt batch size, so peak prefill work stays bounded as concurrency grows.
Chunking is internal and does not change the visible prompt, logits, or generated text.

CUDA engines retain freed scratch allocations for reuse across forward passes. Memory maintenance
trims excess cached allocations while idle and under memory pressure. Reserved CUDA memory can
therefore include reusable scratch space as well as live tensors.

`f8e4m3` stores K and V at half the bytes of BF16. CUDA accepts FP16, BF16, or FP32 activations and
converts at cache-write time; paged decode and prefill (fattn) dequantize K and V with their scales as
they load them, without gathering a full-precision cache. Scales are immutable for the cache lifetime, so
previously written entries are never reinterpreted. The default scale is 1.0, matching the common
vLLM and SGLang serving configuration. FP8 cache is not currently supported for MLA layouts.

## KV cache quantization

`q2` through `q8` store K and V at that many bits a value, and `qK/qV` gives K and V their own (`q8/q4` is 8-bit K
with 4-bit V). Each head's row is rotated by a 32-point Hadamard transform, which evens out channels with outsized
values, then each group of 32 values is scaled by its largest and rounded to the grid; a group's scale adds half a
bit a value. fattn reads the cache in place, dequantizing as it loads, with the query and output rotated to match.

| Cache | Bytes a value | vs BF16 |
|---|---|---|
| `auto` (BF16) | 2 | 1x |
| `f8e4m3` | 1 | 2x smaller |
| `q8` | 1.06 | 1.9x smaller |
| `q8/q4` | 0.81 | 2.5x smaller |
| `q6/q4` | 0.69 | 2.9x smaller |
| `q4` | 0.56 | 3.6x smaller |
| `q3` | 0.44 | 4.6x smaller |

K is the sensitive half. Teacher-forced perplexity through the cache
([measurements](https://github.com/christopherthompson81/inference.rs/blob/master/docs/investigations/kv_cache_quant_investigation.md)):

| Cache | Dense model, every layer attends | Hybrid model, a quarter of the layers attend |
|---|---|---|
| `f8e4m3` | +0.6% | +0.2% |
| `q8` | +0.1% | no change |
| `q8/q4` | +0.1% | +0.2% |
| `q6/q4`, `q6/q3` | +1-2% | +0.5-1.9% |
| `q4` | +22% | +0.6% |
| `q3` | +67% | +2.6% |

`q8/q4` is the safe default when memory is short: lossless on both and smaller than FP8. Hybrid models, whose
few attention layers hold the whole cache (Qwen3.5 and later), take `q4`.

### Per-layer types

Low K widths cost most in a few layers, and which ones depends on the model: in dense Qwen2 and Qwen3 models layer
0 dominates (Qwen2.5-Coder 3B's perplexity goes from 5.35 to 24.3 when only layer 0's K drops to 3 bits), while the
hybrid Qwen3.5 and Qwen3.8 models and TinyLlama have no such layer. So a quantized cache type is applied per layer:

- A measured model's **profile** (`crates/inference-nn/src/paged_attention/kv_profiles.json`, recognized by its
  layer count, hidden size, head counts and head size, so every quantization of its weights matches) names the
  layers that stay at `q8`. Qwen3 0.6B at `q4` keeps layers 0 and 5 at `q8`, which takes its perplexity cost from
  +22% to +1.9% for 7% more cache.
- A model **without a profile** keeps its first cached layer at `q8` when the type's K is under 6 bits.
- `--pa-cache-layers` (and `paged_cache_layers` on a model or a manager load) sets layers itself, last:
  `0=q8,20-27=q6`. `uniform` stores the type in every layer, without a profile or the rule.

The web UI's slot settings show the plan a quantized cache will get under **Per layer**: the profile the model's
shape matches (the model manager's inventory reads it from the GGUF metadata or `config.json`), or the default rule;
**Uniform** and **Custom...** (typed overrides) set the rest. The load logs the plan it chose (`PagedAttention KV
cache type is q4, with the Qwen3 0.6B profile`). Quantized widths
can differ by layer; `auto` and `f8e4m3` cannot be mixed with them. `scripts/kv_layer_sweep.py` measures a model's
layers against a running server and prints its profile entry.

Quantized caches run on CUDA with fattn's kernels (Turing or newer) and the HND layout, for models whose K and V
heads have equal sizes that are a multiple of 64; other models fail to load with the reason. MLA models (DeepSeek)
are not supported.

## Flash attention vs FlashInfer

Paged attention and flash attention compose; both can be on simultaneously. They are not the same backend:

- Flash attention (fattn) is built with the `cuda` feature and runs on compute capability 7.5+; `flash-attn-v3` (Hopper) adds FA3 ahead of it for the standard attention path. See [cargo features](/reference/cargo-features/).
- The paged decode and prefill kernels are built with the `cuda` feature as part of paged attention; fattn serves those too.

## CUDA graphs

CUDA graphs capture a fixed decode step once and replay it with new token and metadata inputs. This reduces CPU launch overhead during autoregressive decoding. It does not change model math, sampling, or output quality.

They are enabled by default for supported CUDA decode paths. To disable them for comparison or debugging:

```bash
INFERENCE_RS_CUDA_GRAPHS=0 inference serve --paged-attn on -m <model>
```

They require a CUDA build and a CUDA device, and they apply to decode, not prompt prefill.

### Replay preconditions

Graph replay is attempted only when all of these are true:

- The model implementation declares CUDA decode graph support.
- Paged attention is active, and fattn decodes every layer (a layer fattn cannot read gathers, which a graph cannot replay).
- The step is single-token decode (`q_len == 1`), not the initial prompt chunk or a prefix-cache hit.
- The request is not using a speculative proposer path.
- The graph key matches the input shape, dtype, cache metadata shapes, and context bucket.

If any condition is not met, inference.rs runs the normal CUDA path.

<details>
<summary>Capture and replay internals</summary>

The first time a decode shape is seen, inference.rs runs a normal warmup forward, captures a graph for that shape, uploads it, and caches it. Later matching decode steps copy the current input ids and paged-attention metadata into graph-owned buffers and replay the graph.

Supported pipelines also capture common batch sizes during startup. Ordinary single-token decode reserves metadata capacity through 2048 context tokens, bounded by the available cache and sliding window. This lets startup graphs handle changing admission and drain batches within that capacity; longer contexts can still require another capture.

The decode graph cache holds a small number of recent graph entries. New batch sizes, tensor shapes, or metadata layouts can trigger another capture.

If capture or replay fails, CUDA graphs are disabled for that loaded pipeline and a warning is logged. Generation then continues through the normal CUDA path.

</details>

### When graphs help

CUDA graphs help most when decode is limited by CPU launch overhead or many small kernels. They are most useful with paged attention because the paged metadata gives the graph stable tensor shapes while the values inside those tensors change from step to step. They usually do little for prompt prefill, where larger matrix and attention kernels dominate.

For apples-to-apples benchmarking, keep the same prompt length, generation length, batch size, paged-attention mode, and FlashInfer setting across runs.
