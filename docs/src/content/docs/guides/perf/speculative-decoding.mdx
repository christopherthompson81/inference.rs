import { Tabs, TabItem } from '@astrojs/starlight/components';

Speculative decoding lets a smaller assistant propose future tokens while the target model verifies them in parallel. inference.rs exposes this through the MTP (Multi-Token Prediction) API: attach an assistant checkpoint and the engine drafts several tokens per target step.

Output stays exact: every accepted token is verified by the target model before it is emitted.

:::caution
The target must run with [paged attention](/guides/perf/paged-attention/) (the default on CUDA). Loading fails with an error if paged attention is off.
:::

<Tabs>
<TabItem label="CLI">

```bash
inference run -m google/gemma-4-E4B-it --quant 8 \
  --mtp-model google/gemma-4-E4B-it-assistant \
  --mtp-n-predict 6
```

`--mtp-model` accepts a Hugging Face id or a local path. The same flags work with `inference serve`. See [run](/reference/cli/run/) and [serve](/reference/cli/serve/) flag references.

</TabItem>
<TabItem label="Python">

```python
import inference_rs as ir
from inference_rs import types as t

spec = t.EngineSpec(
    model=t.ModelSelectedMultimodalPlain(model_id="google/gemma-4-E4B-it"),
    runtime=t.RuntimeSpec(
        isq="8",
        mtp=t.MtpSpec(model="google/gemma-4-E4B-it-assistant", n_predict=6),
    ),
)
engine = ir.Engine(spec)
```

`t.MtpSpec` mirrors the `--mtp-*` flags: leave `model` unset to load the checkpoint's built-in head (`--mtp`), and `draft_sampling` takes a `t.MtpDraftSampling`.

</TabItem>
<TabItem label="Rust">

```rust
let model = inference::ModelBuilder::new("google/gemma-4-E4B-it")
    .with_mtp_model("google/gemma-4-E4B-it-assistant", Some(6))
    .build()
    .await?;
```

`with_builtin_mtp(n_predict)` drafts with the head built into the checkpoint instead. The MTP builder methods exist on every model builder.

</TabItem>
</Tabs>

`--mtp-n-predict` controls how many assistant tokens are proposed per step. If it is omitted, inference.rs reads `num_assistant_tokens` from the assistant's `generation_config.json` and falls back to 6.

## Supported models

| Mode | Target models | Assistant model | Status |
|---|---|---|---|
| MTP | Gemma 4 | Gemma 4 assistant checkpoints (`--mtp-model`) | Supported with paged attention |
| MTP | Qwen3.5 (dense and MoE), Qwen3.8 | Built into the checkpoint (`--mtp`) | Supported with paged attention |
| DFlash / DFlash 2 / DSpark | Qwen3.5, Qwen3.8 | DFlash and DSpark draft checkpoints (`--mtp-model`) | Supported with paged attention |

Legacy target/draft speculative decoding has been removed. New speculative decoding features use the MTP proposer/target path.

## Qwen3.5 / Qwen3.8

Qwen3.5 and Qwen3.8 checkpoints, dense and MoE, ship a multi-token prediction head (`mtp.*` weights) sharing the target's embeddings and `lm_head`. Pass `--mtp` to load it; no separate assistant model is needed:

```bash
inference serve -m Qwen/Qwen3.8-27B --quant 4 --mtp
```

The head keeps its own paged KV cache alongside the target's, so the KV budget grows by one attention layer. `--mtp-n-predict` defaults to 2 for these heads. Greedy output is equivalent to non-MTP decoding up to floating-point tie-breaks in the hybrid recurrent layers. UQFF artifacts must include the `mtp.*` tensors to use `--mtp`.

## DFlash and DFlash 2 (Qwen3.5 / Qwen3.8)

[DFlash](https://arxiv.org/abs/2602.06036) drafters are small block-diffusion models that propose a
whole block of tokens in one pass, conditioned on hidden states tapped from the target's
intermediate layers. They reach much higher acceptance than the built-in single-token MTP head.
Pass a DFlash checkpoint (a HF id or local path) as `--mtp-model`; inference.rs detects DFlash vs
DFlash 2 from the checkpoint's `architectures` and loads the path selector and dynamic convolutions
when present:

```bash
inference serve -m Qwen/Qwen3.8-27B --quant 4 \
  --mtp-model incoai/Qwen3.8-27B-DFlash2
```

`--mtp-draft-sampling` defaults to `auto`. A DFlash 2 checkpoint uses probabilistic drafting when
its CUDA candidate selector is supported, while DFlash 1 and unsupported devices use greedy
drafting. Pass `--mtp-draft-sampling greedy` to force greedy drafting. Passing `probabilistic`
requires a supported DFlash 2 selector and fails during loading when that path is unavailable.

The maximum automatic draft depth is `min(block_size - 1, 7)`. During serving, inference.rs may use a
shallower depth so the recurrent checkpoint layout fits the configured sequence capacity while
preserving memory for the requested paged KV cache. Pass `--mtp-n-predict` to request a fixed depth
instead. Automatic CUDA serving also adapts the active depth to live load: up to 8 live DFlash
contexts use the full reserved depth, while larger loads use up to 3 drafts. Set
`INFERENCE_RS_DFLASH_ADAPTIVE=0` (or `false`) to disable load adaptation. The drafter's projection
weights are requantized to the target's in-situ quantization type at load; `--mtp-draft-isq` (`mtp.draft_isq`
in a spec or a model manager load) picks their type instead. A GGUF target has no in-situ type, so its drafter
stays BF16 unless one is given: on Qwen3.8 27B, `q4k` keeps the BF16 drafter's acceptance for about a quarter of
its 3.85 GB.

A quantized DFlash drafter is kept in `~/.cache/inference-rs/drafters/` (under `XDG_CACHE_HOME` when set) after its
first load, so later starts read it instead of quantizing again: on Qwen3.8 27B at `q4k` that cuts a start from about
15 s to 7 s. A changed checkpoint, weight type or inference.rs version quantizes again and replaces the drafter's old
file; deleting the directory is always safe.

Acceptance is strongly content-dependent: [incoai/Qwen3.8-27B-DFlash2](https://huggingface.co/incoai/Qwen3.8-27B-DFlash2)
accepts ~7 of 7 drafts on math/code and much less on thinking-mode reasoning traces, which are out
of its training distribution. As everywhere in this engine, drafts are verified by the target:
greedy output is byte-identical to non-speculative decoding.

## DSpark (Qwen3.5 / Qwen3.8)

DSpark drafters (DeepSeek's DeepSpec, also trained with SpecForge) are DFlash drafters with a low-rank Markov head:
each draft's logits gain a bias keyed on the previous token, so the drafts chain across the block. They draft from
every row of the block, the anchor included, so a block of 7 yields 7 drafts and an 8-wide verify. Pass one as
`--mtp-model`; inference.rs detects it from `architectures` (`DSparkDraftModel`, `Qwen3DSparkModel`):

```bash
inference serve -m Qwen/Qwen3.8-27B --quant 4 \
  --mtp-model RadixArk/Qwen3.8-27B-DSpark --mtp-n-predict 7
```

Drafting is greedy (the Markov chain picks the argmax at each position, as the reference does), and a drafter that
ships its own YaRN scaling uses it. Not yet supported: the confidence head's early cutoff (the head loads but is
unused), the speculators export format (`DSparkSpeculator`), reduced draft vocabularies, and non-Qwen3 backbones.

Published DSpark drafters attend to the whole context rather than a window, so they run without CUDA graphs and keep
about 20 KB of drafter cache per context token on Qwen3.8 27B (5 layers, 8 KV heads), more than a q3 target cache.
On the RTX 3090 they accept about as many tokens per step as DFlash 2 (3.0 against 3.5 on the same coding and
review prompts) and decode slower, so DFlash 2 stays the better choice where one exists.

## Gemma 4

Gemma 4 assistant checkpoints are MTP drafters for Gemma 4 target models. See the [`google/gemma-4-E4B-it-assistant`](https://huggingface.co/google/gemma-4-E4B-it-assistant) model card for the upstream checkpoint. A downloaded checkout works too:

```bash
inference run -m google/gemma-4-E4B-it --quant 8 \
  --mtp-model ./gemma-4-E4B-it-assistant \
  --mtp-n-predict 6
```

Non-paged KV-cache MTP is intentionally disabled for now, which is why paged attention is required (see the note at the top).

The target and assistant configs must match where the implementation requires it, including vocabulary size and target hidden size. Mismatches fail at load, before generation starts.

## Notes

MTP remains exact: accepted output is verified by the target model before it is emitted. Throughput gain depends on how many proposed tokens the target accepts and on the cost of the target verification pass.

MTP supports batched generation and constrained decoding.

MTP is configured at launch time only (CLI flags, the Python engine spec or the Rust model builder). There is no per-request HTTP field to toggle it; load the server with the assistant attached and every request uses it.
